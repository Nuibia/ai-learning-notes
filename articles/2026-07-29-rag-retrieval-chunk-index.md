# 我以为用了向量检索就是 RAG，直到我追完了检索结果的去向

> 完整案例代码：[RAG 检索与 Chunk Runtime Demo](https://github.com/Nuibia/ai-learning-notes/tree/main/examples/2026-07-29-rag-retrieval-runtime)

我以前接触过 RAG，也做过一套比较熟悉的流程：

```text
清洗文档
→ 切分内容
→ 调用 Embedding
→ 写入向量数据库
→ 根据用户问题进行相似度检索
```

因此，我一直很自然地把 RAG 和向量检索联系在一起。

但这次学习中，我遇到了一个看起来很简单的问题：

> 一个系统检索出了相关文档片段，却没有把片段交给 LLM，只是直接展示搜索结果，它算 RAG 吗？

我的第一反应并不确定。

继续追踪完整链路后，我才发现：判断一个系统是否属于 RAG，关键不在于它使用关键词检索、向量检索还是混合检索，而在于检索结果最终去了哪里。

## RAG 的判断点在最后一步

RAG 的全称是 Retrieval-Augmented Generation，也就是“检索增强生成”。

可以把它拆成三步：

```text
Retrieval：检索相关证据
Augmented：把证据加入模型上下文
Generation：LLM 根据问题和证据生成回答
```

因此，下面这个系统只是搜索：

```text
用户提问
→ 检索相关文件
→ 直接展示文件列表或文档片段
```

而下面这个系统才构成完整的 RAG：

```text
用户提问
→ 检索相关片段
→ Runtime 把问题和片段一起交给 LLM
→ LLM 根据片段生成回答
```

这也意味着，向量检索并不是 RAG 的必要条件。

如果系统使用关键词检索找到相关片段，再把片段交给 LLM 生成回答，它依然可以构成 RAG。

反过来，即使使用了 Embedding 和向量数据库，如果最终只展示搜索结果，没有进入 LLM 的生成过程，它仍然只是语义搜索。

## 关键词、向量和混合检索解决的是召回问题

检索方式决定“怎样找到候选片段”，但不决定系统是否属于 RAG。

### 关键词检索

关键词检索适合精确标识符，例如：

```text
ERR_AUTH_403
ORDER_20260729
refund_policy_v2
```

这类内容不需要推测语义，只要精确匹配即可。

### 向量检索

向量检索适合自然语言表达。

例如下面两句话没有完全相同的关键词：

```text
定制商品不支持退款
定做的东西能退钱吗
```

Embedding 可以把它们转换到同一个向量空间，根据语义距离找到更接近的内容。

### 混合检索

真实系统经常同时使用两种方式：

```text
用户问题
├─ 关键词检索：寻找错误码、订单号、专有名词
└─ 向量检索：寻找语义相近的自然语言片段
        ↓
Runtime 合并候选并重新排序
        ↓
截取最终片段
```

混合检索并不意味着把所有候选都交给 LLM。

Runtime 通常还会维护两层数量：

- `candidateK`：每路检索器最多返回多少候选；
- `finalK`：重排以后，最终有多少片段进入 LLM。

例如：

```text
关键词检索返回 20 条
向量检索返回 20 条
→ Runtime 合并、去重和重排
→ 最终只把 5 条交给 LLM
```

候选太少，可能漏掉真正证据；候选太多，又可能增加噪声，污染模型回答。

## 正确片段没有进入 LLM，属于哪一层失败？

假设用户询问：

> 定制商品付款 20 天后可以退款吗？

知识库中存在两条规则：

```text
片段 A：普通商品付款后 30 天内可以退款。
片段 B：定制商品不支持退款。
```

如果 Runtime 只召回片段 A，LLM 很可能回答：

> 可以，退款期限是付款后 30 天。

这个回答虽然由 LLM 生成，但根因并不一定发生在生成阶段。

真正的问题是：片段 B 没有进入模型上下文。

另一种情况是，片段 B 在检索结果中排第 4，但 Runtime 只取 Top-3。此时向量数据库已经找到了正确证据，最终链路仍然失败了。

因此，更准确的分析方式是：

```text
正确证据没有进入 LLM
→ 检索、召回、重排或 Top-K 截断问题

正确证据已经进入 LLM，模型仍然无依据地回答错误
→ 生成、Prompt、引用约束或模型能力问题
```

不能只因为最终答案由 LLM 输出，就把所有错误都归因于 LLM。

## distance 不是正确率

向量数据库可能返回这样的结果：

```js
[
  { id: "A", distance: 0.12 },
  { id: "B", distance: 0.78 }
]
```

在当前 Demo 的约定中，`distance` 表示向量距离，越小代表越接近。

正确排序应当是：

```js
hits.sort((a, b) => a.distance - b.distance);
```

如果写成：

```js
hits.sort((a, b) => b.distance - a.distance);
```

就会把距离更远的 B 排到前面。

此时 Embedding 没有出错，向量数据库也返回了正确数值，问题发生在 Runtime 对字段语义的理解上。

另外，`0.12` 也不能直接理解为“回答有 88% 的概率正确”。

它只是特定模型、特定距离算法和特定向量库契约下的距离值。怎样排序、是否设置阈值、怎样与关键词结果合并，仍然属于 Runtime 的策略。

## Chunk 不是 Embedding 自动切出来的

这次学习还纠正了我的另一个模糊认识。

我以前会把下面这些步骤统称为“Embedding 入库”：

```text
清洗
→ 切片
→ 向量化
→ 建立索引
```

实际上，它们属于不同职责：

| 环节 | 负责什么 |
| --- | --- |
| 数据清洗 | 去除乱码、导航、广告和无效内容 |
| 结构解析 | 识别标题、段落、表格等文档结构 |
| Chunk 切分 | 生成适合检索的文本片段 |
| Embedding | 把已经切好的文本转换成向量 |
| 向量数据库 | 保存向量、原文和 metadata，并建立检索索引 |

Chunk 通常由应用侧的数据处理脚本或 Runtime 生成，不是 Embedding 模型自动完成的。

某些平台把上传、切分、向量化和入库封装成一个接口，看起来像是一次操作，但内部职责仍然存在。

## 固定长度切分为什么不够？

在 Demo 的第一版中，我先按 Markdown 标题切分章节，再对超长章节按照固定字符数继续切分。

测试可以运行，但实际输出出现了问题：

```text
商品已经使用或损 | 坏时
E | RR_AUTH_403
```

“损坏”被拆成两部分，错误码 `ERR_AUTH_403` 也被截断了。

增加 overlap 可以让相邻 Chunk 重复一部分内容，但它只能降低风险，不能保证切分点一定合理。

更可靠的组合策略是：

```text
先按标题保留业务结构
→ 再按段落或完整句子组合 Chunk
→ 超过最大长度时停止装入
→ 只有单个句子本身仍然过长，才使用字符切分兜底
```

修改后，Demo 能完整保留：

```text
规则三：商品已经使用或损坏时，需要人工复核责任。
规则四：遇到系统异常时，请保留 ERR_AUTH_403 等错误信息。
```

所以，Chunk 策略不是“固定 500 字”这样一个孤立参数，而是结构边界、自然语言边界、最大长度和异常兜底共同组成的策略。

## 修改 Chunk 规则后，旧向量还能继续使用吗？

不能。

Embedding 处理的是具体 Chunk 文本。Chunk 规则变化后，原来的两个片段可能变成五个新片段，文本边界和语义范围都发生了变化。

这时需要重新执行：

```text
按新规则生成 Chunk
→ 为每个新 Chunk 重新计算 Embedding
→ 写入新索引
```

但生产环境中也不能直接先删除旧索引，否则新索引构建期间会出现检索空窗。

更稳妥的流程是引入索引版本：

```text
v1 继续提供检索
→ 构建 v2 Chunk
→ 计算 v2 向量
→ 验证 v2 的召回结果
→ 将线上检索切换到 v2
→ 删除或归档 v1
```

每个 Chunk 可以携带：

```js
{
  documentId: "doc-17",
  indexVersion: "v2",
  chunkId: "doc-17:v2:3",
  section: "售后细则"
}
```

这样 Runtime 才能准确区分新旧版本，并按 `documentId + indexVersion` 清理过时数据。

过时的并不是原始文档，而是旧 Chunk 对原文的索引表示。

## metadata 不只是展示来源

我以前更容易把 metadata 理解为页面上的来源信息，例如：

```text
来源：refund-policy.md
章节：售后细则
```

这只是它的一种用途。

metadata 还可以参与检索范围控制：

```js
{
  tenantId: "company-a",
  documentId: "doc-17",
  indexVersion: "v2",
  section: "售后细则"
}
```

假设向量库同时保存甲、乙两家公司的内部制度。甲公司的用户查询时，不应该先检索全库 Top-5，再让 LLM 忽略乙公司的片段。

因为乙公司的高相似片段可能占满 Top-5：

- 甲公司的有效片段没有进入候选；
- 无权访问的数据已经进入 Runtime；
- LLM 还承担了本不应该由它承担的权限过滤。

正确链路应当是：

```text
Runtime 校验用户身份
→ 确定 tenantId 和 activeIndexVersion
→ 在允许范围内执行向量检索
→ 再计算 Top-K
```

对于隔离要求更高的系统，还可以按租户拆分独立 namespace、独立索引，甚至独立向量数据库。

但无论采用哪种方案，检索范围都必须由 Runtime 根据已经验证的身份决定，不能直接相信前端传来的 `tenantId`。

## Demo 最终验证了什么？

今天的 Demo 没有调用真实 Embedding 和 LLM，而是使用可重复运行的 Stub，把注意力放在 Runtime 的数据流和失败边界上。

最终覆盖了：

- 普通搜索与 RAG 的区别；
- 关键词、向量与混合检索；
- `candidateK` 和 `finalK`；
- distance 排序方向；
- Embedding 模型不一致时阻断检索；
- Markdown 结构解析与 Chunk metadata；
- 自然语言边界优先的切分策略；
- v1/v2 索引构建、切换与清理。

9 个自动化测试全部通过。

这些测试不能证明真实 Embedding 模型的召回质量，但可以证明 Demo 中的 Runtime 控制流符合预期。

## 我今天真正弄懂了什么？

以前，我更关注“是不是用了向量数据库”。

现在我判断一条 RAG 链路时，会继续追问：

1. 检索结果有没有真正进入 LLM？
2. 正确证据在哪一步丢失了？
3. Chunk 是怎样生成的，有没有破坏语义边界？
4. Embedding 模型和索引版本是否一致？
5. metadata 是否在 Top-K 之前限定了检索范围？
6. 回答错误究竟属于召回失败，还是生成失败？

RAG 不是“接上向量数据库”就结束了。

它是一条由数据预处理、检索、重排、上下文组装和 LLM 生成共同组成的完整链路。只有看清每一层由谁负责，才能在结果出错时找到真正应该修改的位置。

下一步，我会继续学习 RAG 回答、引用与拒答：当证据已经进入 LLM 后，怎样让回答明确引用来源；当证据不足时，怎样让系统承认不知道，而不是继续编造。
