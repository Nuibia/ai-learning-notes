# Pi、Hermes、LangChain 越看越乱，我为什么决定从 100 行 Agent Loop 开始

我一直想做一个真正属于自己的文字创作 Agent。

这并不是突然冒出来的想法。过去一段时间里，我已经用 Codex 和 Claude Code 做过内容创作、知识整理和学习记录等实践。它们都能帮我写东西、执行流程、调用工具，但我始终觉得自己只是在使用别人的 Agent。

我想亲手做一个。

真正开始查资料以后，我很快就陷入了选择困难：Pi、Hermes、LangChain、LangGraph、Pydantic AI……这些名字看起来都和 Agent 有关，却又不像在解决同一类问题。

我最初的问题也变成了：到底应该 fork 一个开源 Agent，还是从零手撸？

## 我把不同层级的东西放在了一起比较

这次学习中，第一个被纠正的认知，是我把“成品 Agent”和“开发框架”混成了一类东西。

Pi 是一个已经可以使用的极简 coding agent harness。Hermes Agent 也是成品实现，强调自托管和自进化。它们回答的是：“一个完整 Agent 可以被做成什么样？”

LangChain、LangGraph、Pydantic AI 则是开发框架。它们提供工具注册、状态管理、工作流编排等积木，帮助开发者搭建自己的 harness。

而 Harness 本身不是某个具体产品，它是一层架构：主循环、工具系统、上下文、记忆、安全护栏和终止条件共同组成的运行环境。

完整 Agent 可以先粗略理解成：

> Agent = LLM + Harness

当我把这些概念分层以后，“Pi、Hermes 和 LangChain 应该选哪个”这个问题本身就不再准确了。它们不是同一层级的三个候选项。

## Chatbot 和 Agent 的差异不是“能不能调用工具”

我原来还把 Chatbot 理解得过窄，觉得它主要就是 AI 客服，只能产生文字，不能真正改变外部世界。

但 Chatbot 同样可以写代码、分析文档、做方案，甚至通过产品封装间接调用工具。Chatbot 与 Agent 更本质的差异，不是能力列表，而是控制权在谁手里。

- Chatbot 由人主导：人不断发出下一步指令，模型回答当前问题。
- Agent 由 LLM 主导：人在开始时给出目标，LLM 在循环中决定下一步是回答、调用工具、继续观察，还是停止。

这个区别对我很重要。因为我想做的不是一个“增加了几个按钮的聊天框”，而是一个可以围绕创作目标自己推进步骤的系统。

## 最小 Agent 的核心，其实就是一个 Loop

去掉框架和产品包装以后，最小 Agent Loop 可以写成很短的伪代码：

```python
while step < max_steps:
    response = llm(messages, tools)

    if response.has_no_tool_call():
        return response.text

    result = runtime.execute(response.tool_call)
    messages.append(result)
```

LLM 并不会亲自执行工具。它只输出调用哪个工具、传入什么参数的意图；真正读取文件、写入内容、访问接口的是 Runtime 中的代码。

工具描述也不是给人看的普通注释，而是提供给模型的说明书。名称、用途、参数和边界描述不准确，模型就可能选错工具或传错参数。

Loop 也不能无脑运行。它至少需要三类终止条件：

1. 模型不再请求工具，直接返回最终结果；
2. 达到最大步数或资源预算；
3. Runtime 判断继续循环已经没有收益，或者结果正在恶化。

我在小说工作流里已经见过“问题越改越多”的情况。循环次数更多，并不等于结果一定更好。一个可靠的 Agent 必须允许停止，甚至允许明确失败。

## 三个看似细节、实际很容易踩坑的地方

理论自测让我发现，自己还有三个关键概念没有真正说清楚。

第一个是 prompt caching。

它不是把全部聊天历史永久缓存起来，也不能让上下文无限增长。它只是 provider 对每次请求中重复的 prompt 前缀做缓存，让相同输入前缀在后续调用时按更低价格计费。历史太长仍然需要截断、摘要或重组。

第二个是流式 tool calling。

真正的坑不只是 UI 显示得快不快，而是 parser 必须正确处理两件事：同一次响应中的 `text` 与 `tool_use` block 可能交错出现；一个工具调用的参数也可能被拆成多个 chunk。只有完整 block 收齐以后，Runtime 才能执行工具。

第三个是长篇创作上下文。

几十章正文不能一股脑塞进模型。需要把世界观、角色、时间线、当前章节目标和关键历史压缩成更小的资产，再在每次创作时稳定拼接真正需要的信息。摘要、结构化状态、RAG 和设定文件不是互斥答案，而是不同信息类型的组织手段。

## 为什么我决定暂时不用框架

最后，我选择从零手写一个最小 Agent Loop，不先 fork Pi，也不先上 LangChain 或 LangGraph。

这不是说框架没有价值，而是我当前最缺的不是编排能力，而是对 Agent 最小运行机制的亲手理解。

如果一开始就使用框架，我可能很快得到一个“能跑”的结果，却仍然说不清楚：

- messages 是怎样增长的；
- tool call 是怎样被解析和执行的；
- 工具结果为什么要重新喂给模型；
- Loop 在什么情况下停止；
- 流式参数分片应该在哪里组装；
- 错误应该交还给 LLM，还是由 Runtime 直接终止。

这些问题都藏在框架抽象下面。先手写一遍，再去读 Pi 的源码或使用 LangGraph，我才能知道框架替我解决了什么，也能判断它的抽象是否适合我的创作场景。

## 我的文字创作 Agent 路线

我把后续实践拆成四个阶段。

第一阶段只做内核：Python + Anthropic SDK，实现一个最小 Agent Loop，只提供 `read_file` 和 `write_file` 两个工具。目标不是“功能丰富”，而是能看清每一次模型决策、工具执行和消息回填。

第二阶段补工程能力：工具注册表、流式解析、SQLite 会话持久化，并接入一个自己熟悉的内容创作场景。

第三阶段才进入真正的创作差异化：`SOUL.md` 管文风，`WORLD.md` 管世界观，`CHARACTERS.md` 管人物，`OUTLINE.md` 管大纲，再逐步实验摘要、RAG 和状态结构。

第四阶段是可选进阶：MCP client、子 Agent 评审回路，以及 Writer、Observer、Auditor、Reviser 之间的协作。

## 这次只是理论毕业，还不是实践毕业

我完成了理论自测和三道纠错题，也确定了路线，但还没有开始写代码。

这条边界必须说清楚。能解释 Agent Loop，不等于能正确处理真实 API 返回；知道流式参数会分片，也不等于已经写出了稳定 parser；列出上下文压缩方案，更不代表它们已经在长篇创作中被验证。

下一步不是继续比较更多框架，而是打开编辑器，写出第一个最小循环。

等这个约 100 行的 Agent 真正跑通以后，我再回头看 Pi、Hermes 和 LangGraph。到那时，我看到的就不再是一堆互相竞争的名词，而是不同团队对同一组工程问题给出的答案。

我想做的也不只是一个会生成文字的聊天框。

我要亲手理解，模型的意图是怎样经过 Runtime 变成真实行动的。
